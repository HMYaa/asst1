# Program 5: BLAS `saxpy`

## 1. 作业目标

`saxpy` 计算：

```text
result[i] = scale * X[i] + Y[i]
```

本题的输入规模是 `N = 20,000,000` 个 `float`。需要编译运行程序，比较：

- `saxpy_ispc`：单个 ISPC gang 并行，主要利用 SIMD。
- `saxpy_ispc_withtasks`：ISPC tasks 并行，利用多核加 SIMD。

需要回答的问题是：tasks 带来多少加速，为什么性能表现是这样，以及是否还能接近线性加速。

## 2. 需要掌握的知识点

### SIMD 与 tasks 的分工

ISPC 的 `foreach` 把独立循环迭代映射到 SIMD lanes。`launch` 则把整个数组切成多个 task，交给多个 CPU worker 并行执行。

因此：

- 无 tasks 版本主要利用单核 SIMD。
- 有 tasks 版本同时利用多核和 SIMD。

### 算术强度

算术强度（arithmetic intensity）是 Roofline Model 中常用的专业概念：

```text
算术强度 = 浮点运算次数 / 数据搬运字节数
单位：FLOP/Byte
```

它回答的问题是：每从内存系统搬 1 byte 数据，程序能做多少计算。如果读进来的数据只参与很少计算就被丢掉，算术强度低；如果一份数据被反复用于很多计算，算术强度高。

算术强度通常不是按单条指令算，而是按一个自然的工作单位算，例如一个数组元素、一个像素、一个矩阵 tile，或者一个主要 kernel。对 `saxpy` 来说，最自然的单位是一个元素：

每个元素做 2 次浮点运算：

```text
scale * X[i] + Y[i]
```

普通 store 下，每个元素的内存流量近似是：

```text
读 X[i]      4 bytes
读 Y[i]      4 bytes
写 result[i] 4 bytes
RFO 读 result 所在 cache line  4 bytes/element
```

所以作业中：

```cpp
TOTAL_BYTES = 4 * N * sizeof(float)
```

是合理的。虽然源码看起来只有两个 load 和一个 store，但普通写入未命中缓存时通常会触发 write-allocate / read-for-ownership，把目标 cache line 先读入缓存。

算术强度约为：

```text
2 FLOPs / 16 bytes = 0.125 FLOP/byte
```

这个值很低，所以 `saxpy` 是内存带宽受限程序，而不是计算受限程序。

如果按整个数组计算，结论相同：

```text
计算量 = 2N FLOPs
内存量 = 16N bytes
算术强度 = 2N / 16N = 0.125 FLOP/byte
```

实际机器上的字节数会受 cache 命中、RFO、预取、对齐、NUMA 和编译器生成代码影响，所以算术强度通常是对关键循环的性能建模，而不是逐条机器指令的精确审计。它的主要价值是先判断优化方向：程序更可能受计算限制，还是受内存带宽限制。

一个常用判断方式是和机器平衡点比较：

```text
机器平衡点 = 峰值算力 / 峰值内存带宽
```

如果程序算术强度低于机器平衡点，通常更可能 memory-bound；如果高于机器平衡点，通常更可能 compute-bound。

## 4. 性能解释

从第一性原理看，`saxpy` 的每个元素都互相独立，所以它确实很容易并行化。问题不在依赖，而在资源瓶颈。

如果程序是计算受限的，增加核心数可能带来接近线性的加速。但 `saxpy` 每个元素只做一次乘法和一次加法，却要搬运多份内存数据。多核并行后，CPU 核心很快不再是瓶颈，瓶颈转移到内存子系统。

因此 tasks 有明显收益，因为更多核心可以发起更多内存请求，提高内存带宽利用率。但它不会接近逻辑 CPU 数量的线性加速，因为所有核心最终共享有限的内存带宽。

### 为什么前面的程序不一定遇到同样问题

判断瓶颈不能只看“指令是否简单”，而要看“每份数据被拿进来后做了多少计算”。

一个常见误区是：看到程序里都是简单循环、简单乘加，就认为它们的性能瓶颈应该类似。实际不是这样。瓶颈由“计算量和数据搬运量的比例”决定，而不是由单条指令看起来复杂还是简单决定。

`saxpy` 是：

```text
读 X[i]、Y[i]，写 result[i]，只做 1 次乘法和 1 次加法
```

也就是搬很多数据，只算一下。

前面的程序虽然也由简单指令组成，但单个数据元素通常会参与更多计算：

- Mandelbrot：一个像素可能迭代几十到几百次，每次都有乘法、加法和比较，最后才写一个像素结果。
- `clampedExp`：读入一个 value 和 exponent 后，可能根据 exponent 做多次乘法。
- `sqrt`：读入一个数后，会做多轮迭代逼近平方根。

这些程序更接近：

```text
搬一份数据进来，反复算很多次
```

而 `saxpy` 更接近：

```text
搬一份数据进来，算一次就丢掉
```

所以 prog5 更容易暴露内存带宽瓶颈。循环一直在执行并不代表 CPU 一直在有效计算；当下一批 `X[i]`、`Y[i]` 还没从内存层次结构送到核心时，计算单元就可能处于等待数据的状态。

另一个误区是：认为“程序一直在一个循环里跑”，CPU 就应该一直在算。对 `saxpy` 来说，循环每轮都依赖新的 `X[i]` 和 `Y[i]`。当数组远大于 cache，并且每个元素基本只用一次时，数据必须持续从内存层次结构流向 CPU：

```text
内存 -> cache -> CPU -> cache -> 内存
```

CPU 的乘加单元很快，可能很快算完当前已经到达的数据。但下一批数据能否及时到达，取决于 cache、预取、load/store buffer、内存控制器和内存通道的吞吐。现代 CPU 可以同时发起多个内存请求来隐藏延迟，但这个能力有上限。一旦所有核心请求数据的总速度超过内存系统能提供的速度，核心就会出现等待。

因此，“被内存限制”在这里主要不是指某一次 load 的单点延迟，而是指单位时间内能搬运的数据总量有限，也就是带宽有限。`saxpy` 每个元素计算太少，无法用足够多的计算去覆盖持续搬运数据的成本，所以表现为 memory-bound。

## 5. 是否还能大幅提升

常规 ISPC task 版本已经主要受内存带宽限制。只靠重排循环、增加 task 数量、手动展开等表面优化，通常不会带来数量级提升。

一个有理论依据的优化方向是减少普通 store 的 write-allocate 流量。代码中额外实现了 `saxpy_ispc_streaming_withtasks`，用 ISPC `streaming_store` 对 `result` 做非临时写，目标是绕过 cache，减少 RFO 流量。

这个优化需要满足两个条件：

- 写地址按 SIMD 宽度对齐。
- 结果短期内不会被再次读取。

本实现保持原有 task 框架，只新增一个 streaming-store task 版本。为了满足对齐要求，`resultStreaming` 使用 32 字节对齐分配，streaming task 的 span 也按 `programCount` 对齐。

但在本机实测中，streaming-store 版本没有提升，反而比普通 task 版本慢：

```text
普通 task ISPC:       8.885 ms
streaming-store task: 9.274 ms
```

这说明在当前机器、当前数据规模和 runtime 下，普通 store 已经表现不错，streaming store 的额外约束和硬件实现没有转化为实际收益。这个结果也支持本题的核心结论：`saxpy` 的主要瓶颈是内存系统，不能期待通过简单代码改写获得接近线性加速。

### 为什么有理论依据的 streaming store 会变慢

`streaming_store` 的出发点是减少普通 store 的 RFO 流量。这个方向是对的，但它不是无条件更快。它能否获益取决于硬件、数据规模、访问模式、线程数、cache 状态和编译器生成代码。

本题场景下可能变慢的原因包括：

1. **普通 store 已经很接近硬件可达到的带宽。**  
   task 版本已经达到约 `33.542 GB/s`。如果内存通道、内存控制器或 socket 间带宽已经接近饱和，减少一部分理论流量不一定能变成端到端时间下降。

2. **streaming store 有更严格的写入约束。**  
   非临时写通常希望地址对齐、连续、整 cache line 写入。为满足这些约束，代码需要按 `programCount` 对齐 task span，并处理尾部元素。这些控制逻辑很小，但当核心瓶颈已经不是算术时，额外指令也可能抵消收益。

3. **结果会马上被 `verifyResult` 读取。**  
   streaming store 的典型适用场景是“写出大量结果，并且短期内不再读取”。但本 benchmark 写完后立即校验 `resultStreaming`。计时区间不包含校验本身，但 streaming store 绕过 cache，可能使后续读无法从热 cache 中获益；更重要的是，这说明该访问模式并不是 streaming store 最理想的使用场景。

4. **多线程下瓶颈是共享内存系统，而不是单线程写分配。**  
   如果只有一个核心在跑，减少 RFO 可能更明显。但 tasks 版本让很多 worker 同时读写大数组，瓶颈变成内存系统整体吞吐、NUMA 路径、写合并缓冲和调度开销的组合。此时单个 store 指令的理论优势可能被系统层面的限制淹没。

5. **benchmark 数值本身有波动。**  
   本机多次运行中 streaming-store 版本通常略慢，约 `0.91x` 到 `0.96x`。这个差距不大，但方向稳定说明它不是显著优化。对于性能作业，不能只挑一次有利结果，而应报告可复现趋势。

因此，这里出现“理论上减少内存流量，但实测没有变快”的情况并不矛盾。性能优化不是只看指令局部性质，而是看端到端瓶颈是否真的被改变。我们的 streaming-store 版本改变了写策略，但没有改变这个程序主要受内存系统吞吐限制的事实。

## 6. 教训

1. **先建性能模型，再决定优化点。**  
   `saxpy` 的第一性原理模型告诉我们它是低算术强度、内存带宽受限程序。这个判断比“多线程”“SIMD”“手动展开”这些局部技巧更重要。

2. **优化假设必须被测量验证。**  
   streaming store 是合理假设，不是错误方向。但实测显示它没有收益，所以最终结论必须服从数据。

3. **不要把局部减少指令或流量等同于整体加速。**  
   减少 RFO 只是影响内存流量的一部分。端到端性能还受 cache、NUMA、写缓冲、task 调度、编译器代码生成和内存控制器影响。

4. **负结果也有价值。**  
   这个实验说明常规 task ISPC 已经相当接近该机器在此 workload 下的有效带宽。没有加速不是失败，而是帮助我们确认真正瓶颈的位置。

5. **报告要诚实区分“优化思路”和“优化结果”。**  
   一个优化有理论依据，不代表它在当前机器上成功。正确写法是说明出发点、实现约束、实测结果和结论，而不是为了优化而优化。

## 7. 结论

本题最重要的结论不是“多加线程就会更快”，而是要先判断程序受什么资源限制。

`saxpy` 的工作量完全可并行，但算术强度太低。tasks 可以提高内存带宽利用率，因此有加速；但当内存带宽接近饱和后，继续增加并行度无法带来线性收益。`TOTAL_BYTES` 使用 `4 * N * sizeof(float)` 是因为普通写入会产生 write-allocate / RFO 流量。streaming store 是合理的优化假设，但在本机实测中没有带来性能提升。
