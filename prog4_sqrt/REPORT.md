# Prog4: Iterative sqrt 分析报告

## 1. 作业目标

本题不是要求改写一个更快的 `sqrt`，而是通过同一个迭代算法观察 SIMD 和多核并行的性能边界。

需要完成三件事：

1. 运行原始随机输入，报告无 tasks 的 ISPC 加速比和有 tasks 的 ISPC 加速比。
2. 构造一种输入，让 ISPC 相对串行的加速比尽量大，并解释为什么。
3. 构造一种输入，让无 tasks 的 ISPC 相对串行的加速比尽量小，并解释为什么。

我没有做第 4 问的 AVX2 intrinsics 加分项，因为它会引入另一套实现，和前三问要观察的核心现象不是同一个层次。

## 2. 需要掌握的知识点

### SIMD lane

本题 ISPC 使用 `--target=avx2-i32x8`，也就是 8-wide SIMD。可以把一次 SIMD 执行理解成 8 个 lane 同时处理 8 个输入。

理想情况是 8 个 lane 做完全相同数量的工作。这样一条向量指令能同时推进 8 个有效元素。

### SPMD on SIMD

ISPC 写法看起来像每个元素都有自己的控制流：

```ispc
while (pred > kThreshold) {
    guess = (3.f * guess - x * guess * guess * guess) * 0.5f;
    pred = abs(guess * guess * x - 1.f);
}
```

但在 SIMD 硬件上，同一个 gang 里的 lane 仍然共享向量指令。当某些 lane 已经收敛、某些 lane 还没有收敛时，ISPC 会用 mask 关闭已经完成的 lane，但循环还要继续执行，直到这个 gang 里最慢的 lane 也完成。

所以关键不是“每个元素能不能独立算”，而是“同一个 SIMD 组里的元素需要的迭代次数是否接近”。

### 任务并行

`sqrt_ispc_withtasks` 把数组分成多个 task，让多个 CPU core 同时工作。它解决的是跨核心并行问题；无 tasks 的 ISPC 主要解决单核 SIMD 问题。

因此：

- SIMD 加速主要取决于 lane 利用率。
- tasks 加速主要取决于多核利用率、任务划分和机器核心数。
- tasks 不能消除单个 SIMD gang 内部的 lane 分歧，但可以让更多 core 同时处理不同 gang。

## 3. 第一性原理分析

这个程序每个元素的计算量不是固定的。输入值越接近收敛困难区域，牛顿迭代次数越多；输入为 `1.0` 时，初始猜测已经很好，几乎不用迭代。

串行版本的总时间近似是：

```text
T_serial ≈ 所有元素迭代次数之和
```

无 tasks 的 SIMD 版本不是简单除以 8。它按 8 个元素一组执行，每组时间更接近：

```text
T_simd ≈ 每个 8-wide 组内的最大迭代次数之和
```

原因是一个 SIMD 组里只要还有一个 lane 没完成，整个向量循环就还要继续跑。

所以判断输入好坏的核心指标是：

```text
lane 利用率 ≈ 组内平均有效迭代次数 / 组内最大迭代次数
```

如果 8 个 lane 都慢，但慢得一样，利用率高，SIMD 适合。

如果 1 个 lane 很慢，7 个 lane 很快，串行只为那个慢元素付一次代价；SIMD 却让整个 8-wide 组被这个慢 lane 拖住，利用率低。

## 4. 输入设计

代码保留原有框架，只在 `main.cpp` 中增加输入模式：

```bash
./sqrt random
./sqrt best
./sqrt worst
```

### random

原始基线：`values[i]` 随机分布在 `[0.001, 2.999]`。

### best

所有输入都设为 `2.999f`。

这个值接近收敛较慢的边界，但仍在可收敛区间内。不能直接用 `3.0f`：从当前迭代公式看，初始 `guess = 1` 且 `x = 3` 时，下一步会变成 0，之后无法恢复，会导致循环无法收敛。

选择 `2.999f` 的理由：

- 串行版本每个元素都要做较多迭代，基准时间变长。
- 每个 SIMD gang 的 8 个 lane 迭代次数几乎相同。
- lane 利用率高，SIMD 的相对优势更容易体现。

### worst

每 8 个输入中，第 1 个设为 `2.999f`，其余 7 个设为 `1.0f`：

```cpp
values[i] = (i % 8 == 0) ? 2.999f : 1.f;
```

选择这个模式是因为 ISPC 的目标是 8-wide SIMD。这样每个 SIMD gang 里都有 1 个慢 lane 和 7 个快 lane。快 lane 很快结束，但整个 gang 仍要等慢 lane。

这不是随机制造坏数据，而是直接针对 SIMD 执行模型构造最差 lane 利用率。

## 5. 本机实验结果

测试机器为当前本地环境，不是 Stanford myth 机器。最终提交前应在目标机器上重新跑一遍。

| 输入模式 | serial | ispc | task ispc | ISPC 加速比 | task ISPC 加速比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| random | 1082.900 ms | 295.484 ms | 15.422 ms | 3.66x | 70.22x |
| best | 2791.096 ms | 505.901 ms | 22.253 ms | 5.52x | 125.43x |
| worst | 384.897 ms | 506.039 ms | 25.294 ms | 0.76x | 15.22x |

## 6. 结果解释

### 原始随机输入

随机输入里，不同 lane 的迭代次数不同，所以 SIMD 不能达到理想 8x。这里无 tasks ISPC 是 3.66x，说明有 SIMD 收益，但 lane 分歧和额外控制流损耗吃掉了不少理论加速。

### best 输入

`best` 下所有 lane 的工作量一致，并且每个元素计算量较高。串行时间明显变长，ISPC 时间也变长，但 ISPC 能同时推进 8 个相似 lane，所以相对加速提高到 5.52x。

这说明优化出发点不是“让输入简单”，而是“让 SIMD lane 做相似的工作”。

### worst 输入

`worst` 下串行版本很快，因为 7/8 的元素是 `1.0f`，几乎不用迭代。无 tasks ISPC 却很慢，因为每个 8-wide gang 都被那 1 个慢 lane 拖住，导致 7 个快 lane 大部分时间处于 masked-off 状态。

因此无 tasks ISPC 只有 0.76x，也就是比串行更慢。这正是 SIMD 控制流分歧的代价。

### tasks 的作用

有 tasks 后，程序还能利用多个 CPU core，所以即使 `worst` 的 SIMD lane 利用率很差，task ISPC 仍然比串行快。但 `worst` 的 task 加速比远低于 `best`，说明多核并行没有消除 SIMD 内部的分歧，只是在更多核心上同时承担这个低效率。

## 7. 教训

1. SIMD 不等于自动 8x。理论宽度只是上限，真实收益取决于 lane 是否同时做有效工作。
2. 控制流分歧比指令本身更关键。这里每次迭代的指令不复杂，但迭代次数不同会破坏 SIMD 利用率。
3. 优化前要先建立模型。本题的模型是“串行看总迭代次数，SIMD 看每组最大迭代次数”。
4. 构造输入不是作弊，而是用可控实验隔离变量：`best` 隔离高 lane 利用率，`worst` 隔离低 lane 利用率。
5. 边界值要验证收敛性。`3.0f` 看起来是最慢点，但对当前公式会卡住；工程上不能只凭图或直觉选值。

## 8. 结论

Prog4 的核心结论是：SIMD 性能的关键不是“循环能不能并行”，而是同一条向量指令里的 lane 是否有相似的控制流和工作量。

`best` 输入提高了 SIMD 加速，因为 8 个 lane 都在做相同数量的有效迭代；`worst` 输入让无 tasks ISPC 慢于串行，因为每个 gang 都被一个慢 lane 拖住。tasks 进一步利用多核，但不能从根本上修复 SIMD lane 分歧。
